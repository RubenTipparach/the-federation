# CLAUDE.md

Project rules for Claude Code working in this repository. These are binding. When a rule
here conflicts with a general habit or a suggestion in the design docs, this file wins.

---

## 1. Writing Style

**Never use em dashes (Unicode U+2014) in any text, anywhere.** This applies to every kind of output:
documentation, code comments, commit messages, PR bodies, in-game text, UI strings, log
messages, and chat replies. It matters most for end user facing text, but the rule has no
exceptions.

Use instead, depending on what the sentence is doing:

| Instead of an em dash | Use |
|---|---|
| Introducing a definition or explanation | A colon |
| A parenthetical aside | Commas or parentheses |
| A hard break between two independent clauses | A period, and two sentences |
| A range of numbers | A plain hyphen, as in `10-25 minutes` |

Also avoid en dashes (Unicode U+2013) for the same reason: use a plain hyphen in ranges so
the text stays plain ASCII and greppable.

Both characters are named by codepoint here rather than written out, so that the rule stays
mechanically checkable. The whole repository should contain zero of either character:

```sh
# matches U+2014 and U+2013 by codepoint, so this command itself stays clean ASCII.
# LC_ALL is required: \x{...} above 0x7F needs a UTF-8 locale.
LC_ALL=C.UTF-8 grep -rnP '\x{2014}|\x{2013}' \
  --include='*.md' --include='*.cs' --include='*.gd' --include='*.tscn' . && echo FAIL
```

## 2. 3D Models

**Every finished model must be delivered as `.obj` or `.gltf` / `.glb`.**

- The deliverable is a file the user can open and edit in Blender or any standard DCC tool.
- Never leave a model as engine only data: no Godot `.tres` / `.res` mesh resources as the
  authoritative source, and no meshes that exist only in a scene file.
- Prefer `.gltf` / `.glb` when the model carries materials, hierarchy, or animation.
  Use `.obj` for static geometry where simplicity matters more.
- Commit the editable source file. The Godot import of that file is a build product, not
  the source of truth.
- If a model is generated by a script, the script's output must still be a written `.obj`
  or `.gltf` file on disk. Do not build meshes at runtime. See §5.

---

## 3. Art

**Every finished art asset must be delivered as a `.png`.**

- This covers textures, sprites, icons, UI elements, and concept art.
- No proprietary or engine only formats as the deliverable.
- Preserve alpha where the asset needs it.
- If a lossy or compressed format is needed for shipping, it is generated from the `.png`
  at build time. The `.png` remains the committed source.

## 4. Architecture and Code Quality

### 4.1 Modularity and reuse

**Avoid divergent code paths that share functionality at all costs.** This is the highest
priority engineering rule in the project.

- If two places need the same behavior, they call the same code. No copies, no near copies,
  no "this one is slightly different so I forked it."
- When a second caller needs a variation, parameterize or extend the shared implementation.
  Do not clone it.
- Before writing anything new, search for an existing implementation and extend it.
- If you find existing duplication while working, say so. Do not add a third copy.

Concretely for this project: the combat simulation, the ship fitting validator, and the
damage model must exist exactly once, in a shared library used by the client, the server,
and any tooling. The fitting screen's projected stats must be computed by the same code that
resolves a real battle. Two implementations guarantee divergence.

### 4.2 SOLID

Follow the SOLID principles when writing code.

- **Single responsibility:** one class, one reason to change. Split anything that has grown
  two jobs.
- **Open / closed:** extend behavior by adding types or configuration, not by editing
  a growing `switch` in the middle of existing logic.
- **Liskov substitution:** a subtype must be usable anywhere its base type is, with no
  special casing at the call site.
- **Interface segregation:** small, focused interfaces. Callers should not depend on methods
  they never use.
- **Dependency inversion:** depend on interfaces, not concrete types. Inject dependencies
  rather than constructing them inside the consumer, so systems can be tested in isolation.

## 5. Godot Rules

### 5.1 No procedural scenes or meshes

**Avoid fully procedurally generated scenes or meshes.**

- Scenes are authored as `.tscn` files and committed. Do not build node trees in code at
  runtime as the normal way of constructing things.
- Meshes are authored as files (§2) and imported. Do not generate geometry in code.
- Instantiate and configure prebuilt scenes. Do not assemble them node by node in a script.
- If something genuinely cannot be statically authored, raise it before implementing and get
  agreement on a documented exception. Do not decide this silently.

### 5.2 Scenes are structure, code is behavior

**Gameplay and functionality live in code, not in scenes, object definitions, or settings.**

- A `.tscn` defines what exists and how it is arranged. It does not define what things do.
- No gameplay logic embedded in scene data, no behavior expressed through node
  configuration, no rules encoded in inspector values.
- Scripts attached to nodes should be thin: they wire the node to a system that lives in
  plain, testable code outside the scene tree.
- The simulation must be runnable and testable without instantiating a scene.

### 5.3 Node structure

Make scene nodes as modular and statically defined as possible.

- Small, single purpose scenes that compose, rather than large monolithic ones.
- A scene should be usable on its own and testable in isolation.
- Prefer composition of child scenes over deep inheritance chains of scenes.

### 5.4 Settings and configuration

All settings live in one of:

1. A **config file** (preferred): a committed, human readable, diffable file.
2. A **Godot resource or library system**, where the engine genuinely requires it.
3. A **Godot node**, only as a last resort.

Node based settings beyond engine defaults should be avoided where possible. Anything a
designer will want to tune belongs in a config file, not scattered across inspector fields
in scene files, because inspector values are hard to diff, hard to review, and easy to
change by accident.

Never hardcode tuning values inline in gameplay code.

## 6. UI Work

**Always get user approval of a mockup before implementing a UI element.**

- Present a mockup and wait for approval before writing implementation code for any new UI
  element, screen, or layout.
- A mockup can be an image, an HTML sketch, a text wireframe, or a rendered artifact,
  whichever communicates fastest.

Approval is **not** required up front for:

- Small changes to already approved UI.
- Bug fixes.
- Text, spacing, or styling corrections within an approved design.

When unsure whether a change is small enough to skip approval, ask. The cost of asking is
much lower than the cost of building the wrong screen.

Note: the shipyard fitting screen is the most used screen in this game and is effectively a
UI heavy product in its own right. It needs mockup approval per screen, not one blanket
approval for the whole system.

## 7. Documented Exceptions

Exceptions to the rules above live here, with the reason. Nothing may be treated as an
exception until it is listed in this section and agreed.

- **Data driven 2D chart controls may paint via `Control._draw()`.** The SSD shield
  ring and the 12 sector arc wheel are live data visualizations; their content cannot be
  statically authored because it IS the data. The nodes are authored in their scenes, the
  scripts only paint sim state and report clicks, and no node trees or meshes are
  constructed. Agreed via the approved mockups and the instruction to build them
  (2026-07-30).
- **Tactical overlays compose committed unit meshes, placed by code.** The 3D combat
  view's arc wedges, shield segments, range rings, and beams are instances of committed
  `.obj` files (written by `tools/gen_meshes.py` per section 2), statically authored as
  scene children, with code doing rotation in 30 degree steps, scaling, and authored
  material selection only. This is the placement pattern section 7 anticipated and it
  keeps section 5.1 intact rather than excepting it.

**One candidate is pending a decision.** Rendering roughly 3,000 hexes with smooth zoom and
several frequently changing per hex overlays is hard to do with statically authored nodes
alone. `docs/06-technical-architecture.md` §9 raises this and does **not** adopt a procedural
approach, because that would conflict with §5.1. The likely reconciliation is to author the
hex geometry as a committed mesh file per §2 and let code handle only *placement* of
instances, which keeps the rule intact. This needs a decision before any map rendering work
starts.

## 8. Repository Context

The repository holds the design documents, the itch.io deploy pipeline (`scripts/`,
`.github/workflows/`, `build.config`), and the first playable prototype: a shared
simulation library under `src/sim/` (headless tests in `tests/`), UI screens under
`scenes/` and `src/ui/`, committed mesh and data assets under `assets/` and `data/`.
See `README.md` for the document index, `docs/08-build-and-deploy.md` for the pipeline,
and `docs/07-roadmap.md` for the build order and current status.

Two conventions the pipeline establishes, worth keeping:

- **CI workflows stay thin.** Build logic lives in `scripts/`, which CI and developers
  both run. Putting build steps in workflow YAML creates a second implementation that
  drifts from the local one, which section 4.1 forbids.
- **`build.config` is the only place** build versions, targets, and deploy coordinates
  are written, per section 5.4. Do not hardcode them in scripts or YAML.

The rules above apply from the first line of code, especially §4.1. Retrofitting shared
implementations after divergence has set in is far more expensive than starting shared.

## 9. Automation and Self Check-ins

**Do not schedule recurring self check-ins, polling loops, or re-arming reminders unless
the user explicitly asks for them.** This includes waking the session on a timer to re-check
a pull request, a CI run, a deploy, or any other external state.

- Finish the work, report the state once, and stop. Do not schedule a follow up "just in
  case."
- A check-in that is already running must not re-arm itself after the user asks for it to
  stop, or after the thing it was watching is resolved.
- Reacting to an event that arrives on its own, such as a pull request webhook or a task
  completion notification, is fine. It is the self scheduled timer that is off by default.
- When the user does ask for a recurring check, follow their interval and their stop
  condition, and end the loop as soon as that condition is met.
